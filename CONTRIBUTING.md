# Contributing to vizscript

Thanks for helping! This guide covers the development setup, the architecture and how to get a change merged. The coding conventions and architecture rules live in [AGENTS.md](AGENTS.md); they apply to human and AI contributors alike.

## Development setup

Requirements: Node.js ≥ 24 (the version in `.nvmrc` is the default), pnpm 12 and Docker.

```sh
pnpm install
cp .env.example .env        # then set APP_SECRET (openssl rand -base64 48)
pnpm db:up                  # starts Postgres via docker compose
pnpm dev                    # API on :3333 (migrates on start), web on :5173
```

- http://localhost:5173/playground works without signing in.
- Public repositories open without signing in (`/repos`, type `owner/name`). To list and open your own, sign in with a GitHub [fine-grained token](https://github.com/settings/personal-access-tokens/new) with read access to _Contents_ and _Metadata_.
- The web dev server proxies `/api` to the API.

### Environment

| Variable               | Purpose                                                                                                                      |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`         | Postgres for the API, migrations and the API e2e tests                                                                       |
| `APP_SECRET`           | Signs sessions and encrypts stored tokens; at least 32 characters                                                            |
| `SECURE_COOKIES`       | `true` when served over HTTPS                                                                                                |
| `PORT`                 | API port (default `3333`); the web dev server reads `API_PORT` for its proxy                                                 |
| `GITHUB_API_URL`       | GitHub REST API (default `https://api.github.com`); GitHub Enterprise: `https://<host>/api/v3`                               |
| `GITHUB_RAW_URL`       | Raw file contents (default `https://raw.githubusercontent.com`, or `https://<host>/raw` for Enterprise)                      |
| `GITHUB_WEB_URL`       | GitHub's web pages, e.g. the token page linked on sign-in (default `https://github.com`, or `https://<host>` for Enterprise) |
| `GITHUB_SERVER_TOKEN`  | Optional token of the server for signed-out layout checks of public repositories (a higher GitHub limit); needs no scopes    |
| `TYPE_CACHE_MAX_BYTES` | Size the type registry's cache (`type_cache`) may grow to: bytes or `512MB` / `2GB`, default `1GB`                           |

### Docker

`docker compose up --build` runs Postgres, the API (which migrates on start) and the web app behind nginx on http://localhost:8080. It needs `APP_SECRET` in the environment.

### Working files

`tmp/` (scratch files) and `local/` (notes and drafts worth keeping) are git-ignored. Use `tmp/` instead of the system temp folder.

## Architecture

```
apps/
  web/              Vue 3 + Vite + UnoCSS (Tailwind preset) + Monaco
  api/              NestJS (Fastify) + Kysely + node-pg-migrate
packages/
  core/             Language-agnostic graph IR, layout, id reconciliation, edit ops
  lang-typescript/  JS/TS backend: Babel AST → graph
  lang-gdscript/    GDScript backend: own error-tolerant parser → graph
  lang-python/      Python backend: Lezer syntax tree → graph
  lang-rust/        Rust backend: Lezer syntax tree → graph
  canvas/           Framework-agnostic Canvas2D renderer and interaction controller
  workbench/        Workbench layout model: views, zones, folds, presets, validation
  api-contract/     Types shared by web and api
```

Packages are consumed as TypeScript source and have no build step. Only the apps build: the web app with Vite, the API with tsdown.

The canvas's `GraphView` (`graph-view.ts`) is the public API; it inherits nothing and owns the parts, which it passes to each other. The shown document lives in a `Scene` (`scene.ts`): nodes with geometry and positions, wires, reroute points (saved and generated for wrapped exec chains), frames and comment boxes, the spatial index, problems and folded pins, plus what lies where (`hitTest`, `hitWire`, `functionAt`, `wireEnds`) and layout edits (`positions`, `withReroute`, `setReroutes`, `removeKnots`, `levelOf`); it needs only a text measure, so it is tested in Node. Where inline editors open is `inline-edit.ts`. The camera, the canvas size and eased camera moves are a `Viewport` (`viewport.ts`, with pure camera targets: `fitAll`, `focusCamera`, `revealCamera`, `initialCamera`); slides, fade-ins and pulses of nodes are functions of the time in `node-motion.ts`. Drawing is a `Renderer` (`renderer.ts`: grid, frames, comment boxes, wires, reroute points, the drag overlay; `node-renderer.ts`: nodes) that reads the scene, the viewport and a `RenderFrame` (selection, hover, the drag, the time) and changes nothing; `GraphView` advances the motion before each frame. Pointer, wheel and key input is a `Controller` (`controller.ts`) that works on the scene, the viewport and the shared `Interaction` (`interaction.ts`: selection, hover, the drag, the pending wire) and reaches the rest of the view through a `ControllerHost` (`controller-host.ts`), which `GraphView` builds from its own methods; tests drive it through the listeners it registers on a fake canvas. Decisions that need no state live in pure, tested modules beside it: `hit-test.ts` (`hitTest` of a small scene: what a point lands on, in drawing order), `wire-rules.ts` (which wires are allowed, UE's messages, conversions), `align.ts` (UE's alignment tools and keys), `pointer-intent.ts` (`classifyPointerDown`: what a press starts; `Controller.startIntent` carries it out), `node-decor.ts` (parts of a node that need only the canvas, theme and zoom: glows, rims, the SET title, header icons, the latent clock, checkboxes), `font-metrics.ts` (`FontMetrics`: the fonts of a theme and cached text widths, measured again when a theme changes the fonts) and `pointer-drag.ts` (what a drag does while it moves and when it ends: pan and pinch cameras, snapping, marquee reroute points, wire targets with UE's messages and replaced wires, the connect op, hover cursors). Add new logic of that kind there, not to `GraphView`.

### Graph IR

Every language backend lowers its AST into the IR of `@vizscript/core`:

- Functions contain nodes, nodes have pins, and edges connect pins. Exec edges and data edges are kept separate.
- Each node keeps its source range, which drives the code ↔ graph linking.
- Statements become impure nodes on the exec chain; expressions become pure nodes, like Blueprint pure functions.
- `if`, loops, `switch` and `try` become flow-control nodes with a **Completed** output that continues to the next statement, so the exec flow stays a tree.
- Every function, method and callback gets its own graph with an entry node. Top-level statements form a **Module** graph.
- **Calls have a Target pin** (`target`, labelled `this` in TypeScript and JavaScript, `self` elsewhere), right below the exec input, like UE's.
  - A member call is split: its receiver is lowered as a node of its own, so `console.log(x)` is a Get `console` wired into the `this` of a `log` node, and `this.save()` / `self.save()` get the `self` box (`withImplicitSelf`).
  - A free call (`totalPrice(cart)`) has an unwired Target without a range. Wiring a value in writes `value.` before the name (`InputPinMeta.insertSuffix`).
  - GDScript's calls of the script's own and inherited methods (`move_and_slide()`) show the `self` box. Global functions (`print`), constructors (`new X`, `Item::new`, `Item(…)`), conversions and Rust macros have no Target.
  - Use `calleeText` / `callPath` (`packages/core/src/callee.ts`) for the callee as written (`console.log`) instead of the title (`log`).
- **Property reads** are split the same way: `response.ok` is a Get `response` wired into a `.ok` node. A member of the own object (`this.items`, `self.speed`) stays one Get, like UE's member variables, and so does a constant of a type (`State.IDLE`, `Math.PI`; `isTypeConstant`).
- **Rest parameters** (`...data`, `*args`) name their values like UE's Make Array: `data[0]`, `data[1]`, typed by the array's items (`withParamPins`). Without values, a call shows one empty `data[0]` that writes the first one. Such calls get `GraphNode.addPin`: UE's "Add pin ⊕" in the lower right corner (`NodeGeometry.addPin`: the last row when the outputs leave it free, else a row of its own), which runs `addArgument` (it writes the empty `data[0]` too, so a new pin appears next to it). `**kwargs` (`SymbolParam.keywords`) takes keyword pins only.
- Module exports are the module's outputs: `export default x` and `export { a, b }` become **Export** nodes (re-exports show their source), and exported declarations are labelled `export`.

**Stable node ids.** Ids are derived from the function, the kind and the normalized source text, so they survive formatting changes and edits elsewhere in the file. When a node's own text changes, its saved position is matched by its structural path instead. Equal code is counted (`greeter(user)#0`, `#1`), so when one of two equal nodes changes, the other one takes its id: positions are therefore first carried through the change itself (`reconcilePositions` with a `TextChange`: an op's edits, or a diff of the text for typing, undo and redo). Moved code (removed here, the same text inserted elsewhere) is followed to its new place; nested nodes that start at the same offset (`a * b * 100`) are told apart by their length. The diff (`diffEdits`) compares lines, then changed lines token by token, so code an op moved is followed back on undo. Positions of nodes that disappear are kept in the workspace's position memory (the `memory` argument), and a node that comes back with the same id (undo, redo) gets its place again instead of landing on its twin. The layout holds other entries too (keys starting with `~`: reroutes, Gets drawn as wires, comment box colors, loose nodes); `layout-keys.ts` lists every kind, and `reconcileLayout` follows or keeps each through a re-parse, so a new kind added there can't be lost. The workspace saves the entries a re-parse moved to new ids (renames, edited text), so a reload finds every node at its place; entries of nodes that are gone stay stored (undo, a discarded draft or another branch may bring the old code back).

**Parsing runs in a Web Worker,** so large files don't block the UI. The web app only imports language backends inside the worker. One worker serves the whole page (`graph/worker-connection.ts`); each workspace talks to it through its own `GraphClient`. Its calls are typed in `graph/protocol.ts` (`WorkerCalls`: request and response of each). Requests are queued in the page and sent one at a time: the editor's parse replaces a queued older one (`key`), library and npm declarations and the saved version wait for the rest (`background` / `priority: 'low'`), and a closed workspace's queued requests fail with a `CancelledError` (`isCancelled`). A worker that fails or takes over 60 s is replaced; after repeated failures before any answer (e.g. its chunk is gone after a redeploy) requests fail with a hint to reload.

### Graph edits

Graph changes are `GraphOp`s. Each backend turns them into minimal text edits on the original source, normally through the shared `applyTextOp` with its own `StatementSyntax`. A few rules that keep edits predictable:

- **Auto-casting** (UE's autocast): `TypeSystemInfo.conversions` lists each language's conversions between pin types (`Conversion` in `packages/core/src/conversions.ts`, templates with `$value`: `String($value)`, `str($value)`, `$value.to_string()`). The canvas allows a wire that one of them converts (`findConversion`, message "Convert number to string") and sends it as `connect` with `convert`; `connectData` writes the template around the value (`applyConversion` adds parentheses before a postfix template). One-argument calls of a conversion function are lowered as compact pure nodes (`conversionCall`), like UE's autocast node; as a statement of their own they stay ordinary calls. Moving wires (Ctrl/⌘-drag) never converts.
- **Deleting and unwiring never removes other nodes.** The code holds only nodes connected to the exec flow; whatever an edit leaves without a consumer stays in the graph as loose graph-only nodes, like UE's unconnected nodes. In the code, calls stay (they run in the flow: `return load(path)` → `load(path);` and `return;`, a deleted statement keeps its calls, `keptCalls`, and a deleted value node its calls, `keptInputs`), while pure values leave it (`keptValue` in `wire-ops.ts` for Alt + click, Break Node Links, wiring over an input and moving wires). The web app then keeps the nodes the edit took out of the code (`use-kept-nodes.ts`: the nodes before the edit minus those after it, via `renamedNodes`, minus the deleted and the hidden ones): `looseCode` in core turns each part wired together into the code of a loose group, the body of a deleted block as statements, a value as an expression, with inputs fed from outside as the placeholder; they are made again as floating nodes (`floatingNodes`), at the places of the nodes they stand for, and inputs the code still feeds stay wired (graph-only). One undo step with the edit (`recordCodeOverlay`). Deleting nodes of a loose group keeps the rest of it (`deleteLoose`: the group written into a copy of the code, the same `looseCode` there).
- **Wiring an unconnected value** into a later input moves it there. A call only moves into the statement right after it, so the order of side effects never changes.
- **Adding a node after a nested call** (e.g. after the call in `return f(x)`) first stores the call's result in a variable.
- Edits go through Monaco, so code edits and graph edits share one undo history with layout changes.

### Graph-only edits

Like UE, a graph may be in states the code can't hold yet: an exec wire broken with Alt + click, a statement wired somewhere the code can't put it yet, a value wired into an input before it is computed.

- **The overlay:** such ops become graph-only edits (`GraphEdit`: `removeEdge`, `addEdge`, `removeNode`, `addNodes`; `graphEditsFor` in `packages/core/src/graph-overlay.ts`), keyed by node and pin ids like layout entries. While a file has any, the next wire and delete ops join them, so the code follows what the graph shows. Commands (collapse, extract, comments, …) and invalid input keep their error.
- **What is shown:** `applyOverlay` draws them on the parsed graph: graph-only wires are dashed (`GraphEdge.graphOnly`), and `overlayIssues` names what keeps the graph from being code (a statement cut off from the flow, entered twice, a cycle). Those nodes get a NOT IN CODE banner and a dashed outline, and the issues are listed in Problems.
- **Back to code:** `resolveOverlay` (`overlay-sync.ts`, run in the parser worker) writes them once the graph is valid: deletions and statement moves from the difference between the parsed and the shown graph (in the order the code runs; a call inside an expression moves its statement), then each data wire as `connect` / `disconnect`. Every step is an ordinary op on a copy of the text, re-parsed in between; if one fails, the code stays as it is. The result is one edit in Monaco and one undo step with the overlay (`use-layout-history.ts`). Each step must leave code that parses as well as before (more parse errors, or edits that can't be applied, end it as pending with a message about the node), and written floating nodes keep their identity by kind and title (by kind alone only when one candidate is left).
- **Floating nodes:** a node added on empty space (`floatsUntilWired`: anything but pasted code; `addNode` without `after` / `before`, with the `fnId` under the cursor), a node made from a dragged value (`floatValueUse` in `use-graph-overlay.ts`: calls and plain values like `items[0]` alike, only `await` wraps the value where it stands in the code; a floating value joins its group, so the same Get is used; a value of the code is wired in the graph where the template has the placeholder, `feedFloating`, and written by `connect` later), and a SET made by Promote to Variable for a value outside the flow (`floatPromote`: a floating value or call, or an unused value of the code like `items[0];`, which leaves the code in the same undo step), so its exec pins are wired by hand like UE's. In TypeScript, floating nodes are typed in the copy of the code they were made in (`FloatingResult.text`, the worker's `vizTypesAtText`, `typedFloatingNodes`, which also gives calls a pin per parameter from the checker's signature, like code's); a value wired into the empty `this` of a floating call makes the call again with it (`floatReceiver`: `round()` + a floating `Math` become one group `Math.round()`, a value of the code is fed in), so it shows the typed pins of what it calls before it is in the flow; a value picked for an input of a floating node (`new Error()` for a floating Throw's Error) makes its group again with the value written in (`floatInput`, laid out around the kept node), and so does a value typed into a floating node's input (Details or its inline box: `floatLiteral`; a missing argument like `.at()`'s index is inserted, a value it has is found by its text in the node's code, which sends the op wrapped in `inFloating`, applied by core to the group's own code and nodes with the file's syntax; `floatingNodes` keeps their insert offsets relative to that code), and a floating statement not wired into the flow yet can be used as a value too (Throw from a floating `new Error`, `TypeSystemInfo.throwValue`); their types' members travel with the `addNodes` edit, so the action menu lists a floating `console`'s methods and a node added where no code can go (the top level of a GDScript or Rust file, which holds declarations only) become an `addNodes` edit, like UE's new unconnected nodes. An imported name gets its import right away (`addImport`). `floatingNodes` (`overlay-snippets.ts`, run in the worker) writes the template at the end of a function of a copy of the code and keeps the nodes it makes, with ids `overlay:<group>/…` and the code they stand for. They are drawn outside the function frames (`GraphNode.floating`) until something is wired to them; then they join that function. `resolveOverlay` writes them once they are wired into the flow (`addNode` with their code after the wired exec pin) or, for a value, into an input (`setInput`); `placedNodes` pairs them with the written nodes, so wires and positions follow. Deleting them again leaves nothing behind (`compactOverlay`). Other edits of nodes not in the code yet wait until they are wired in.
- **Methods without a receiver:** breaking a method's Target (or deleting the node wired into it) can't be code (`RECEIVER_NEEDED`), so it is graph-only.
  - Like UE, the method's other pins depend on its Target. `graphEditsFor` also drops the wires of its arguments and results (`withCutReceivers`), and `applyOverlay` shows only its exec pins and Target until a value is wired in.
  - Once that happens, `resolveOverlay` first empties its argument list (`clearArguments`; calls inside the arguments stay as statements of their own), then writes the new receiver.
- **Code edits meanwhile:** the overlay follows the code like positions do (`remapOverlay` with `renamedNodes`); edits whose nodes are gone are dropped with a message.
- **Persistence:** the overlay is stored with the file's draft (`overlay` in the repository and local folder drafts, `vizscript:playground:overlays` in the playground) and counts as unsaved. Saving a local folder is blocked while the graph is out of sync (`out-of-sync` of `ScriptWorkspace`); Discard drops it.
- **Loose graph-only nodes** (`splitLoose` in `loose-overlay.ts`): floating groups whose exec pins and data outputs reach no node of the code (wires from the code into them are allowed) aren't part of the program: they don't make the graph out of sync, block saving or send later edits graph-only, and a write leaves them in the overlay. They are stored with the file's layout (`looseLayoutKeys`: `~loose|<group>|<fnId>|<s or v>|<part>|<code part>` keys and `~loosewire|…` for wires from the code; `useLooseNodes` makes them again from their code after loading; when a re-parse gives the code's nodes new ids, `followCode` stores the wires again). Wiring one into the code makes it active, and it is written like other floating nodes.

### Comments, problems and references

- **Symbols** list what a file declares, like UE's "My Blueprint": functions and methods with their parameters and return type, module and class variables, locals, classes, types, enums, GDScript signals and imports (`module` and `imported`: an exported name, `default` or `*`; GDScript's `const X = preload(…)`, Python's from lezer in `imports.ts`). Each backend collects them from its AST in `symbols.ts`; types stay in the language's own syntax (`TypeRef.text`) next to a pin type for colors. Decorators are modifiers as written (`@Get()`, Python's `@staticmethod`; `decoratorsOf` in `graph/symbols.ts` leaves out GDScript's `@export…` and `@onready`), a parameter's are `SymbolParam.decorators`, and type parameters are `typeParams` as written (`T extends object = {}`). A parameter that starts before its name (decorators, `private readonly`) has its whole `range`, so signature edits move and remove it whole; TypeScript writes access levels and `export` after the decorators (`afterDecorators`). The "My Script" panel and the Details panel show them. Imports resolve to repository files through the module references (`importTarget` in `script-workspace/use-imports.ts`); deleting one name of an import list removes just it and its comma (`removeListItem`). The workspace reads imported files (`readFile` from the repository or local folder view, open tabs first), parses them in the worker and keeps what they export (`exportedSymbols`: declarations without ranges into the other file, defaults as text). These `ImportedDeclaration`s go along with every parse and op (`ParseOptions.imports`); `linkImports` gives import symbols their kind, inputs and output, and `completeCallPins` gives calls of imported functions (`fn()`, `ns.fn()`) their pins. Using a name of another file is a `withImport` op: the inner op plus `addImport` in one edit. `DeclarationSyntax.addImport` writes the import per language (`add-import.ts` in TypeScript and GDScript, `imports.ts` in Python) with the shared `joinImport` (add to an import of the same module) and `insertImport` (below the last import, a docstring or `extends`; the file header is `DeclarationSyntax.header` lines plus `leadingDoc`, Python's module docstring, and new variables and types go below it too). Libraries: a backend may know library modules (`LanguageBackend.library`, `libraries`), as stubs in its own language that are parsed like files (Python's standard library in `lang-python/src/stdlib.ts`). Python also reads typeshed's stubs (`apps/web/src/graph/python-stubs.ts`, `TypeshedStubs`) through jsDelivr at a pinned commit (`TYPESHED_COMMIT`; its file listing tells which files exist, `stdlib/` first, then `stubs/<distribution>/`): the files a module re-exports from (`from .api import get as get`, `from .x import *`) are read side by side, then resolved in memory, as stubs import each other in cycles. The backend prepares each for the parser (`LanguageBackend.prepareLibrary`, `preparePythonStub` in `stub-text.ts`): the branches of `sys.version_info` / `sys.platform` checks for the project's Python version, private type variables, aliases and imported private names as `Any`, and module functions that are a private instance's methods (`seed = _inst.seed`) as functions. The backend's own stubs take precedence by name (they return classes, `urlopen()` → `HTTPResponse`, where typeshed says `Any`). To update typeshed, set `TYPESHED_COMMIT` to a newer commit of `python/typeshed`. npm packages are read in the browser from jsDelivr (`apps/web/src/graph/npm-types.ts`): in the version of the lockfile, else the range of the nearest `package.json` that lists them (`graph/npm-project.ts`), the `types` entry of the package (or its `index.d.ts`), and its re-exports, also into other packages (`GraphDocument.reexports`, `withReexports`). A module re-exported as one name (`export * as z from`, or zod's `import * as z …; export { z }`, which the TypeScript backend reports as the same re-export) becomes a constant with the `namespace` modifier and the module's exports as its members (scope `z`), so `import { z }` gets `z.fn()`'s pins; its imports offer no Call (`isUncallableImport`). Imports of libraries name the module directly (`ImportRequest.module`). The dependencies of a file's project (`ProjectDependency` in core: name, declared range, locked version, kind, manifest, local or renamed) come from `graph/project-dependencies.ts`: npm's nearest `package.json` and lockfile (`npm-project.ts`), Python's `pyproject.toml` (PEP 621, PEP 735 groups, uv, Poetry) or `requirements*.txt` with `uv.lock` / `poetry.lock` / `pdm.lock` (`python-project.ts`), and Rust's `Cargo.toml` with workspace inheritance and `Cargo.lock` (`cargo-project.ts`); TOML is read with `smol-toml`. My Script's `+` on Imports adds a library (`script-workspace/AddPackageMenu.vue`, `graph/add-package.ts`): the registry search above, the library's exports to import (`packageOffer` in `use-imports.ts`), the dependency kind (tests and configs default to dev, `build.rs` to build), an `addImport` op, and the manifest changed by `graph/manifest-edits.ts` (a minimal edit: the file's formatting stays, alphabetical order, the section's `^` / `~` / exact style) through the file session's `editFile`, so the manifest is an open tab with unsaved changes; the manifest's text before and after is one undo step with the import (`addLibrary` in `use-library-additions.ts`, `recordFileEdit`: undo sets it back only while it is unchanged since); the lockfile isn't touched (a toast names the install command). An import's "not listed" warning opens the same menu for its library only (`listOnly`: looked up by its exact name, `sameLibrary`, then only the manifest is changed), and the imports' library info is read again afterwards. My Script's Imports show per module what it comes from (`graph/module-info.ts`, `script-workspace/use-module-info.ts`): the locked version (else the range) and the kind of a dependency (dev, peer, optional, build, workspace), `built-in` for modules of the runtime (Node.js's, Python's standard library as typeshed lists it, Rust's `std` / `core` / `alloc`), and a warning for a library no manifest lists; modules that resolve to repository files show nothing. Engine classes: `TypeSystemInfo.classes` lists classes a language knows without an import (`EngineClass` in `packages/core/src/engine-classes.ts`: name, base class, members as portable symbols, `singleton` for global objects like `Input`). GDScript's are a part of Godot 4's class reference written as GDScript declarations (`lang-gdscript/src/godot-api.ts`), parsed once like a script (`godot.ts`). The type picker lists them, the action menu offers the members of a value's class with the inherited ones (`classMembers`) and the members the script inherits from its `extends` class (`engine-entries.ts`), `completeCallPins` names and types the pins of their methods (`CallPinOptions.classes`, `selfClass`; the class comes from the value wired into Target, the variable's declared type, or the script's base class), and inherited properties type their Get nodes. `TypeSystemInfo.inferredType` (GDScript's `:=`) adds "Type of the value" to the type picker of variables (`setSymbolType` with it as the type). Callbacks (functions written as an argument, `on('x', (e) => …)`) have graphs of their own; the TypeScript backend gives them symbols with the `callback` modifier, which core names after their graph (`linkSymbolGraphs`). My Script lists them under Graphs by the function they are written in, nested like an outline and with their line (`callbackGroups` in `graph/symbols.ts`), and Details edits their inputs and output (no name, no modifiers but `async`). "Create callback" writes the language's empty callback (`TypeSystemInfo.callback`: `() => {}`, `lambda: None`, `func(): pass`, `|| {}`) into an input. Values of unknown types still get members: a typed name offers `.name()` / `.name` on a value (`useValue` with `$value.name()`); on a call's unused result it continues the chain in place (`chainedCall` in `insert-ops.ts`: `program.name('x').version()`) instead of binding the result first. TypeScript classes of other files, libraries and imports are offered as `new X()` ("Construct", `ExternalName.kind` `class`), and so are built-in classes (`TypeSystemInfo.constructors`: `new Error()`, `new Map()`): one node each, whose parameter pins come from the checker's constructor signature. `TypeSystemInfo.globals` lists built-in functions offered without an import (`console.log`, `print`); `keywords` keeps reserved words out of the typed entries ("Call return()"), which are also hidden when the menu lists that name already. Action menu entries can carry a `detail` (the signature from `signatureText` and the function's doc comment), shown below the list; favorites and folded categories are kept per browser. The action menu's Get / Set entries list the variables in scope of the function at the menu (`scopeVariables` in `graph-canvas/graph-helpers.ts`: its parameters and locals, module and class variables with their member access; locals declared before the node and, with `ScriptSymbol.visibleIn` from the backend, inside their block: no loop variable after its loop in TypeScript, Rust and GDScript, while Python's outlive it); `fits` compares a pin's type with a callable's first parameter or return type (`signature` in `project-index.ts`), unknown types always fit. The action menu's names of other files come from `project-index.ts`: the first time the menu opens, the workspace reads the exports of up to 150 files of the same language, nearest folders first.
- **Type information** from a type checker refines what the parser found (`packages/core/src/type-info.ts`). A `TypeProvider` answers which type the code has at source ranges (`TypeInfo`: the text as the language writes it, the pin type it maps to, and the type's members). `typeQueries` lists the ranges worth asking about (data outputs, and variables and parameters declared without a type), and `applyTypes` returns a copy of the document with exact output types (`Pin.typeText`), inferred variable and parameter types, and `GraphDocument.typeMembers` for the action menu. Inputs keep the type of what they take, except a SET's value input, which takes its variable's type when the parser had none or only an untyped container (`new Map()` is a `map`), a call's or member's untyped Target (`object`), which takes the type of the value it is used on like UE's Target pins (`isUntypedTarget`: `self` of `builder.require_git(false)` is a `WalkBuilder`), and untyped inputs of operators, selects, Format Texts and GET nodes, which take the type of the output wired into them like UE's wildcard pins (`typeWildcardPins` in `wildcard-pins.ts`, run by `inferTypes` after parsing and by `applyTypes`). The other way round, untyped results of calls, awaits and members (`json.load(…)`, `JSON.parse(…)`) show the type of the inputs they are wired into when those agree (`typeOutputsByUse`, before the wildcard pass), marked `Pin.usedAs` so tooltips say "Any, used as Map"; inputs that take anything (`any`, `object` Targets) don't count, and a type the checker or lookup finds replaces it. Answers of `any` keep the parser's type, empty values (`let x = undefined`) leave a variable untyped (`typesVariable`), and a failing provider leaves the document as parsed (`resolveTypes`). Unwired `void` results lose their pin, like UE functions without outputs. `typeMembers` is keyed by the type's text. An answer for a call's result may carry the `signature` of what the call reaches (the resolved overload in TypeScript, Godot's methods and global functions, the stubs and the file's own methods in Python and Rust); with call options, `applyTypes` then gives the call a pin per parameter through `withParamPins` in `call-pins.ts`, the same completion `completeCallPins` gives calls of declared functions: given arguments get names, types and defaults, missing ones become pins that insert the argument (optional ones with a default fold behind ▼). Graph edits are parsed again in the worker, so the web app sends the checker's latest answers for that text along (`ParseOptions.checked`), and the TypeScript backend applies them while parsing; the lookups of the other languages run inside the parse anyway.
  - TypeScript/JavaScript: `monaco/ts-worker.ts` replaces Monaco's TypeScript worker entry with a subclass of its `TypeScriptWorker` that adds `vizTypesAt`. It asks the worker's own checker (`checker-types.ts`: the smallest node at each range, `getTypeAtLocation`, literals widened, mapped to pin types, members of object types). `monaco/ts-type-provider.ts` calls it for the file open in the editor, only while the editor holds the parsed text; the worker checks the text again (`vizTypesAt` gets it), since the file can change while the request is on its way (a Reset). `script-workspace/use-checker-types.ts` draws the graph with the parser's types first, then with the checker's, and again when the checker gets new files (imports, npm declarations). The action menu offers `typeMembers` of a dragged pin's `typeText` first (`memberEntries` in `graph-canvas/member-entries.ts`), before the members of the file's own types and of engine classes.
  - GDScript: the backend's own lookup (`lang-gdscript/src/type-lookup.ts`) walks the script with scopes, like Godot's analyzer: declared, `:=` and untyped variables (typed by their value or first assignment), For Each items, parameters of Godot's callbacks (`_process(delta)`), members of the script's classes, of Godot's classes (`godot-api.ts`) and of built-in types (`godot-builtins.ts`: `Vector2`, `String`, `Array`, `Signal` …, plus the global functions), operators, casts and `load` / `preload`. `parseGDScriptDocument` applies its answers with `applyTypes`, so the worker's documents and the ops see the same types. `typeMembers` gets the members of built-in types; engine classes keep theirs in `TypeSystemInfo.classes`.
  - Python and Rust: the same kind of lookup in each backend (`type-lookup.ts` for declarations and statements on top of `type-expressions.ts` for expressions, with `type-text.ts` for reading and combining types as text and `builtin-types.ts` for the stubs of the built-in types in `builtins.ts`). Python follows annotations, the first value an unannotated name gets, loops, `with` and `except` targets, classes of the file (fields their methods set through `self`, `__init__` first), imported declarations (`ParseOptions.imports`, including the standard-library stubs) and `await` of `async def` calls. Rust follows `let`s with annotations, patterns (`Some(x)`, `Ok(x)`, tuples), struct fields, `impl` methods, `Self`, turbofish (`sum::<f64>()`, `collect::<Vec<_>>()`), `?`, `.await` of `async fn` calls and unsuffixed literals like rustc (`{integer}` takes the type of the other operand, else `i32`). Imported functions and types (`ParseOptions.imports`: crates from docs.rs, other files of the crate) count too: a type's import carries the `pub` methods and fields of its `impl` blocks and struct as `members` (`exportedTypeMembers` in core, attached in `use-imports.ts`), so `builder.require_git(false)` gets typed pins and a `WalkBuilder` result, and dragging from it lists them. Items of crates named by their path without a `use` (`serde_json::to_string(&x)`, `x: serde_json::Value`) are reported as `GraphDocument.libraryPaths` (`paths.ts`: the first CamelCase segment is the type) and supplied as imports named by the path (`pathDeclaration` in `use-imports.ts`; a head bound by a `use` resolves through it, `usePath`: `overrides::OverrideBuilder` after `use ignore::overrides;`). Paths into modules of the crate itself (`crate::parser::parse`, `super::helper`, `parser::parse` after `use crate::parser;`) read the exports of the module's file: `rustReferences` reports the files of each such module (`modulePath` in `references.ts`), which also makes the module part Ctrl/Cmd+clickable. A crate's own library named by its crate name (`hsml::formatter::format` in a binary of `hsml`: `[lib] name`, else the package name with `_` for `-`) and its path dependencies (`ignore = { path = "crates/ignore" }`, also through `[workspace.dependencies]`; a renamed one by its key) are crates of the repository (`localLibraries` in `cargo-project.ts`): they read the files next to their root (`[lib] path`, else `src/lib.rs`; `moduleFiles` in `crate-types.ts`). Rust files of the repository export what they re-export with `pub use` too (`GraphDocument.reexports` from `rustReexports`: names and globs; `followed` in `use-imports.ts` resolves their modules through the file's references, another crate through `libraryExports`, with `withReexports`, which carries a re-exported type's members along under its new name): ripgrep's `ignore::WalkBuilder` comes from `pub use crate::walk::WalkBuilder` in `ignore`'s `lib.rs`. One-letter generic parameters of imported signatures count as unknown (`from_str<T>` gives a `Result<_>`). Stubs use placeholders (`T`, `K`, `V`, `E`, `Self`) that the lookup fills from the value's type, also in the signatures the action menu shows. SET outputs, loop items, `with` / `if let` bindings and await results carry a source range so the lookup can type them. The action menu names the checked type in its category ("Members of Option<Item>").
- **Types and values:** each backend describes its types as data (`TypeSystemInfo`: basic types with pin colors and default values, container templates such as `list[T]`, an optional and a `promise` wrapper (`Promise<T>` in TypeScript; the picker composes `Promise<Item[]>`), modifiers per kind of symbol), sent to the type picker through the parser worker. `setSymbolType`, `setSymbolValue` and `setModifier` write them; backends validate types (`validType`), quote strings and switch keywords or annotations.
- **Dragging from "My Script"** adds a statement at the end of the function under the drop point (`endOfFunction`, before a final `return`): a call with placeholder arguments, an assignment for Set, or a lone value (the `value` node template) for Get, which the graph shows as unconnected nodes until it is wired into an input.
- **Collapse to function** (`collapse.ts`) takes the statements of the selection (one run in one block), finds its inputs (wires coming in, Gets of the enclosing function's variables, and variables a compound assignment like `+=` or `++` reads) and its result (a variable set inside and read after it), and writes the function and the call with `DeclarationSyntax.extract`. Inputs get the variable's declared type, else the checker's (`Pin.typeText` of its reads), else one the backend writes for its pin type (`ExtractParam.dataType`). One result at most; `return` and jumps out of the selection are refused.
- **Details panel** sections are `DetailsSection` components (collapsed state per section in the browser). Numbers are edited like UE's spin boxes (`NumberField.vue`: drag to change, click to type, ↑ / ↓; the step follows the value's decimals), in Defaults, Default Value, the default values of a function's inputs and node inputs (the widget follows the type everywhere: `valueKindOf` in `symbol-details/value-kinds.ts`); Defaults reuses the variable's value row (`SymbolValueField` with `linked`). Array literals are edited like UE's array properties (`value-fields/ArrayValueField.vue` on the value's Make Array node: "N elements" with ⊕ / 🗑, `[0]`, `[1]` … with a field each, objects folding out into their entries through `PinValueField`, ▼ Insert / Duplicate / Delete, a grip to reorder); the ops are `addArgument`, `removeArgument`, `setLiteral` and `insertElement` / `moveElement` (`array-ops.ts`). Object and dictionary literals get the same kind of rows (`value-fields/ObjectValueField.vue` on the value's Make Object node: "N entries" with ⊕ / 🗑, `key | value | type` rows, ▼ Rename / Delete, double-click a key to rename it); an entry holding an array or object shows its rows across the full width below its key, like UE's nested struct rows. A new entry asks for its key (`addArgument` with `name`); `renameEntry` (`renameObjectEntry` in `add-pin-ops.ts`) keeps how the key is written (bare or quoted, `{ a }` → `{ b: a }`) and refuses computed and number keys. A new element of an array of objects takes the shape of an existing one with empty values (`blankElement`: `{ name: '', price: 0 }`), also for Add pin. An input's default is no node, so an array default (`items: Item[] = []`) is parsed in a host file (`valueHost` in core: the file plus a declaration from `TypeSystemInfo.valueHost`, e.g. `const __value__: Item[] = [];`, parsed through the worker by `PARSE_VALUE`) and edited by `symbol-details/ArrayDefaultField.vue` with the same rows (plus ✕ to remove the default); its ops are wrapped in `inValue`, which each backend applies to that host (`applyInValue`) and shifts back into the real text. Without elements to copy, `blankElement` builds the shape from the element type's fields (`blankValue`). The same value is UE's **Make <Struct>**: dragging from an input whose type lists fields (an interface) offers "Make Item" (`graph-canvas/make-entries.ts`), the `makeValue` op writing `{ name: '', price: 0, quantity: 0 }` into it. Every selection starts with the same header (`DetailsHeader.vue`): a colored bar and icon, the name, and one line with the exact kind and where it lives: `symbolSubtitle` for symbols ("Exported function · Module", "Local variable in totalPrice", "Interface"), `nodeSubtitle` for other nodes ("Flow control", "Operator · pure", from `graph/node-kinds.ts`, shared with the node tooltip), "Comment box" for comment boxes. It only shows; the first section is called **General**, so the kind isn't said twice, and holds the **Name** row (`data-ui=symbol-name`) of functions, types, signals and variables alike (not imports and callbacks). A variable's details follow UE's: the General section (name, type, description, declaration, the operator of a selected SET node, modifiers) and a separate **Default Value** section whose row is named after the variable. Rarely needed rows (uses, scope, location; for nodes the function, kind and id) are in the folded **Advanced** section, with **Source** below it. A selected Get / Set node of a variable shows the variable's sections in place of its own header (`variableOfNode`); the entry or return node of a function, or a call of a function of the file, shows the function's (`functionOfNode`), with a call's own pins under **Call inputs** / **Call outputs**. On a call the function's sections are read-only (name, description, modifiers, inputs with their declared defaults, output): they are edited at the definition, which "Go to definition" in the header opens (the same as F12); only the values the call passes are edited there. A symbol's description is the comment of its entry node (functions, classes) or Set node (variables), written with `setComment` and `doc: true` as a documentation comment (`CommentSyntax.doc`: `block` for `/** */`, or a marker like `##`); edits keep the marker a comment already has. Values of variables are edited only when they are constants, like UE's Default Value: `isConstantValue` in core (literals and collections of them) or a value with fields (`fieldValue`: vectors, colors, enum members). Computed values (`greeter(user)`) are shown read-only in the variable's details and in Defaults, and select the SET node that computes them (`declaringNode`). Constants have no ✕, since a `const` needs its value.
- **Modifiers** offered by Details come from `TypeSystemInfo.modifiers` per kind (`variable`, `constant`, `local`, `member`, `function`, `method`: declaration `keywords`, `access` levels, `flags`) and are written by each backend's `setModifier` in the language's order (`private static async`); TypeScript's `async` also wraps a declared return type in `Promise<…>` and unwraps it again. Script settings (`GraphDocument.settings`) are reported by the backend (GDScript: `settings.ts`) and written with `setScriptSetting`.
- **Wires from a SET** (UE wires a SET's output into inputs): the code reads the variable there, a Get node. A Get made by wiring from a SET's output is remembered in the layout (`~via|<getId>`, `via-wires.ts` in core; `use-via-wires.ts` notes the op and finds the new Get after the re-parse) and drawn as a wire from the nearest SET of the variable before it (`foldVias`, `GraphEdge.via`). Gets that feed the node right after their SET on the exec chain are drawn that way too without being remembered (`adjacentVias`: `const cart = …;` then `totalPrice(cart)`); reads further away stay Get nodes, and so do reads after a loop, also from a SET ending its body: the loop may not run at all. Reads the generated layout wraps to a new row (the SET right of them, e.g. `let total = …` ending a row and `total - total / 2` on the next) stay nodes too: one Get, left of them all, feeds them (`wrappedVias`, decided on `layoutDocument` without saved positions so it doesn't change while nodes are moved); Gets the user wired from a SET, joined or kept win over it. An edit keeps that Get even where the edited graph's generated layout no longer wraps, since the nodes stay where they were drawn (`keptWrapped`). Ops on such wires act on the hidden Get (`throughVias`), so the code is the same either way.
- **Pure node joins** (UE wires one pure node into several inputs and computes it again for each): the code writes the expression at each use, and copies are drawn as one node, the first, with a wire to each use. `pure-joins.ts` in core: `pureSignature` tells whether two pure nodes compute the same expression (kind, title, literals, and what is wired into them), `copyTree` is a copy with the pure parts only it uses (hidden together), and `statementJoins` joins identical expressions within one statement on its own (`item.price * item.quantity + item.quantity`; not across statements, where a value can change in between). Wiring a pure node into another input remembers the copy the code gets as a join (`joinKey`, `joinedCopy` in `use-via-wires.ts`); `foldVias` draws joins of Gets and of pure copies (a join of different expressions is ignored, so changing one copy's code splits them again). Edits of a joined node are written at every copy in one edit (`fanOut` in `script-workspace/pure-join-ops.ts`, `joinedNode` maps a node of the host to the copy's, `GraphOp` `all` merges the ops' edits); breaking one joined wire removes that copy (`disconnect.drop`), deleting the node removes the copies with their parts.
- **Wires** follow UE's spline (`wireCurve` in `packages/canvas/src/bezier.ts`): horizontal tangents growing with the distance, larger going backwards, so backward wires loop out in an S. Exec chains wrapped to a lower row get two generated reroute points in the gap above it (`wrapKnots`, recomputed from the nodes on every layout); moving or removing one saves them like any reroute, and removing them all marks the wire (`noReroutesKey`) so none are generated again. Every segment between reroute points is that spline too; like UE's `ShouldChangeTangentForKnot`, a knot that feeds a point left of the one feeding it is reversed (`reroutedShapes`), so a wire running back turns outside its knots.
- **Comment box colors** are layout entries like reroute points (`~color|<boxId>`, palette index in `x`, `COMMENT_BOX_COLORS`), so they're shared, undoable and never written into the code. The Details search is section-level: `DetailsSection` hides sections whose title, text and field values don't contain the query.
- **Categories** are GDScript export groups: `groups.ts` reads them like Godot's inspector (the parser attaches `@export_group(…)` lines to the next variable) and moves a variable's lines into another group (`setSymbolGroup`).
- **Value fields** (`value-fields.ts` in core): vectors and colors come from `TypeSystemInfo.valueEditors` (GDScript: `Vector2` …, `Color`), enum choices from enum symbols (`members`; Python's enum members are constants of the class) and literal unions. The value is written back as code in the form it had (`Color("#…")` stays html).
- **Reset ↶** compares symbols with the saved version of the file (`baseText` from the view: the file's content from the API, the file on disk, the original sample), parsed once (`baseDoc`); symbols match by id. **Expose on Spawn** (TypeScript) is the `constructor` modifier: parameter properties are collected as class fields, `setConstructorParameter` moves a field into the constructor and back.

Other nodes jump to their code. `parentGraphs` gives the breadcrumb the graphs a callback sits in. The way back: `usagesOf` (in `ScriptWorkspace.vue`) lists the nodes whose definition is a graph, and the entry node's menu offers "Jump to usage in …" for each (`jumpTo`, which switches the focused graph).
- **Focus mode** (`script-workspace/use-focus-mode.ts`): the canvas gets a document with only the focused function (`shownDoc`), so search, menus and layout stay as they are; ops still work on the whole file. Navigation that targets hidden nodes (`selectNodes`, Go to definition) switches the focus first.
- **Type members:** interfaces and object types list their fields and methods (`ScriptSymbol.fields`, TypeScript `symbols.ts`); classes have member symbols, and so do the properties of interfaces and object types (`holdsFields`): Details lists them when their type is selected, like UE's struct editor (`SymbolFields.vue`: name, type, `readonly` from the `field` modifiers, remove; `+ Field` is `addVariable` with the type as scope, written by `DeclarationSyntax.field`: `name: string;`), My Script leaves them out, and they never get a value (`isValuelessField`). Renaming a field changes its declaration only: telling its uses apart needs the checker. The action menu offers them for a dragged value whose type is declared in the file (`memberEntries` in `graph-canvas/member-entries.ts`, written with `useValue` as `$value.price`). `addType` adds an empty type per language (`DeclarationSyntax.typeDeclaration`) after the file's last type, else below its imports or header. `setAssignOperator` switches `=` / `+=` / … of an assignment (`ASSIGN_OPERATORS`).

- **The graph as DOM** (`a11y-layer.ts` in the canvas): `GraphView` keeps an invisible copy of the scene next to the canvas (`data-ui=graph-a11y`, opacity 0, no pointer events, so the canvas still gets every click): one `role=group` per node (`data-node-id`, labeled with the title it draws, plus the full one where that's a word (`SET (Set user)`), "entry", "not in code", its problem), one `role=button` per pin (`data-pin`, "items, string[], output, wired"; unnamed pins of compact nodes by their id, `+`'s `a` / `b`), inline value (`data-literal`, "Value of items[0]: abc") and "Add pin ⊕" (`data-add-pin`), each at the rectangle the canvas draws it. Screen readers read it, and UI tests find targets by role and name and click the middle of their `boundingBox()`. It is synced after every drawn frame (`A11yLayer.sync`) and kept cheap: a camera move rewrites one transform, a node is written again only when it moved, was selected or its content changed (a new document or new problems compare all nodes once); `a11y-layer.spec.ts` counts the DOM writes and bounds the time for 3000 nodes. - **Argument pins** (`arg0`, `arg1`, … written in a call; `ARG_PIN`) know their parameter's default (`InputPinMeta.defaultValue`, from `completeCallPins`). `removeArgument` removes one with its comma and a `...`, `*` or `name=` before it; "Reset to default" removes the last argument and writes the default into earlier ones.
- **Copy and paste** work on code: copying takes the statements of the selected nodes, pasting is an `addNode` with a `code` template that `reindentCode` fits into the target block (indent unit of the file). Paste and duplicate select the new nodes.
- **Moving wires** (Ctrl/⌘-drag of a pin) is one `moveWires` op: the `connectData` edits of every moved wire on the same text, merged (`mergeEdits`: identical edits once, overlapping ones fail). Alignment (`GraphView.alignSelection`) only changes positions.
- **Flow-control nodes** are `{ type: 'flow', flow }` node templates; each backend writes them in its `template` and lists the ones it has in `TypeSystemInfo.flow`.
- **Operators and values** come from `TypeSystemInfo.expressions` (`ExpressionTemplate`: label, category, template with `$1`, `$2` …, result type), one list per backend in its `*_TYPES`. The web app fills `$1` with the dragged value and the other slots with the template's `empty` values (`x * 1`, `a && true`), else for templates without a result type (`+`, `??`) with the empty value of the wire's type (`s + ''`, `emptyInput` in `graph-helpers.ts`), else with the language's `placeholder` (`undefined`, `None`, `null`). A wire dragged from an output becomes a `useValue` op: a lone value after the producing statement, which the graph shows as an unconnected pure node until it is wired. Like UE, a new node is only itself (wired to the dragged pin): an unused call result is used where the call stands (`total();` → `total() + 1;`, no variable for it), and a pure value or Get the new code copies is drawn as the node it was dragged from (a join, recorded in `use-via-wires.ts` like a wire from a pure node, also when a floating node's wire is written later). Defaults that are nodes of their own (`{}`, `new Date()`, `Vector2.ZERO`, `String::new()`: `TypeOption.defaultIsNode`) aren't used for new Set nodes or empty slots; templates leave their inputs to the placeholder (For Each over `undefined` / `None` / `null` / `todo!()`, `throw undefined`, `raise None`). Empty values don't narrow an input's type (`refinesType`), so placeholders take any wire. `looksLikeCode` decides whether typed text is code (numbers, quoted values, known names, also after `!`, `-` or `not`) or text to quote; number and boolean values take such code too (`!response.ok`). Details uses the same rule for an empty value field of an untyped variable or input (`ValueKind` `auto`: `metric` is written `"metric"`, a known name or `{…}` stays code); a field that holds code is marked "code" and edits stay code. A value written into an operand or a receiver gets parentheses where the operator would bind it differently (`operandText` and `substituteValue` in `operand-parens.ts`, one conservative precedence table for all languages: `a * (x + y)`, `(a + b).length`). A value of a loop item or a caught error goes to the start of its block (`bindingBlock` in `insert-ops.ts`). A lone value moves into the input it is wired to, also back to an earlier statement when everything it reads exists there (`inputsReadyAt`), and is not copied where it doesn't. When the overlay writes a new receiver, a lone value's statement is removed only if the connect didn't move it (`strayStatement` in `overlay-sync.ts`). Format Text (template literals, Python f-strings) has UE's **Format** pin first: a pin without code (`InputPinMeta.format`, `formatLiteral`) whose text is the template with `{0}`, `{1}` … for its values, edited on the node like any value and taking no wire. A `setLiteral` on it is `setFormat` (`format-text.ts`, with the language's `TypeSystemInfo.templateOpen`), which writes the new format: `{0}`, `{1}` … keep their values, new numbers get an empty text (`''`, or `""` in a single-quoted template), left out values go, like UE's Format Text pins. With `TypeSystemInfo.templateSpecs` (Python) the Format shows each value's conversion and spec (`{0!r}`, `{1:.1f}`, `{2 = }`), and `setFormat` takes them from the format; a spec that holds values (`{x:{width}}`) isn't shown and stays. Rust's `format!` keeps its Format pin. Await templates (`awaits`: `await $1`, Rust's `$1.await`) wrap a call's result in place (`useValue.awaits`: `await fetch(url)`) and make the function `async` where the language has the keyword (`withAsync`). Duplicating or copying a lone pure node sends `code` with `expression: true`, written as a statement of the language (`asStatement`). The web app runs ops one after another (`script-workspace/use-op-runner.ts`), so an op sees the code the one before left. An op is made on the parsed text: typing not parsed yet is parsed first, and edits that come back after the text changed are dropped. Written edits are an `OpTransaction` (`op-transaction.ts`): only the parse of their result takes what the op noted beforehand (new node placement, kept Gets, kept loose nodes); a parse that started earlier leaves it alone.
- **For Loop:** counting loops are UE's For Loop node (`kind: 'forEach'`, title `For Loop`): First Index, End Index (`<`, `range(…)`, `..`) or Last Index (`<=`, `..=`) pins and the index as the `element` output, with no nodes for the condition or `range(…)` (`lowerCountingLoop` in TypeScript for `for (let i = A; i < B; i++)` and `i += 1`, `countingInputs` in Python and GDScript for `range(B)` / `range(A, B)`, ranges with both ends in Rust). A missing start of `range(B)` is a `0` value inserted as `A, ` when set. The name a loop (or a `catch`) binds is its output pin's name and has the name's range; Details renames it (`renameBinding` in `binding-rename.ts`: the backend's rename of a stand-in local, keeping only the edits inside that node, so another loop's `i` stays).
- **Operator chains** (`a + b + c` of one left-associative operator, `CHAIN_OPERATORS` in `operator-chain.ts`) are one node with pins `a`, `b`, `c` …, like UE's math nodes. Each backend flattens them with `flattenChain`; a parenthesized left side (`(a + b) + c`) stays its own node. `canAddPin` gives them UE's "Add pin ⊕": `addArgument` appends a value that changes nothing (`+ 0`, `* 1`, `+ ''`, `&& true`, else the placeholder), and `removeArgument` takes a value out with its operator while more than two are left. Make Array / List / Vec literals (`arrayElements`; not tuples, sets or `[x; n]`) get it too: `addPinValue` in `add-pin-ops.ts` appends an element with its type's empty value (`0`, `''`, `false`, else the placeholder), on its own line when the elements are (and all on lines of their own once a one-line array grows past 80 columns, with trailing commas), and `removePinValue` removes one with its comma (UE's "Remove array element pin"). Make Object / Dict / Dictionary literals (`objectEntries`; not structs, whose fields are fixed) take the new entry's key as `addArgument.name` (the web app asks for it) and write it with `StatementSyntax.objectEntry`; removing uses each entry's `InputPinMeta.property` range.
- **Spread values** (`...items` in TypeScript calls, arrays and objects; Python's `*items` / `**options`) are input pins with `InputPinMeta.spread` (the token; the pin's range is the value after it), labeled with the token before their name (`spreadName`, `pinLabel`; a spread into a `...rest` parameter is named like its other values, `...items[1]`). Backends mark the inputs that can be spread (`spreadable`: arguments and elements of a collection, not keyword arguments, `**` or object properties), and the pin menu's "Spread value" / "Pass as one value" writes or removes the token (`setSpread` in `spread-ops.ts`).
- **Node look** is decided in core (`geometry.ts`), so layout and canvas agree: `isCompact` (getters, operators and setters drawn without a header), `compactTitle` (`SET`), `pinLabel` (a setter's input is labeled with the variable) and `headerIcon` / `isLatent`. Reading one element (`items[0]`, `name[0]`) is UE's compact GET node, and the value of a key in a map (`prices["tea"]`, a `Record` in TypeScript, `m[&id]` in Rust) its FIND node (`elementAccess` / `isElementGet` in `element-access.ts`): the word between the container and index or key pins and the element, over the container's faded symbol in its colors; the container pin is typed by the container (an array, string or map, else a wildcard), the key by the map's key and the output by the element or value. The action menu offers them from a typed array or map output as "Get" (`$value[0]`) and "Find" (`$value[key]` with the key type's empty value, `TypeSystemInfo.keyReference` before other keys than string literals; not for TypeScript's `Map`, which has no index; `elementEntries` in `make-entries.ts`). Slices (`a[1:3]`, `&v[1..3]`) and optional reads (`a?.[0]`) keep their own titles. Writing one element (`items[3] = x`) is UE's Set Array Elem (`setElement` nodes, `elementWrite`): a function node with Target Array, Index and Item pins; on a map (`d["k"] = v`, a `Record`) it is the map's ADD (`styleElementWrite`), like `m.set(k, v)`. The action menu from an array offers it next to Get (`elementEntries`: `$value[0] = ''`), and from an indexable map without an ADD of its own an Add (`$value[''] = 0`); both float until their exec pins are wired, like every node made from a value, and their values are typed in like any floating node's (`floatLiteral`). Compound writes (`items[0] += 1`), slices and untyped targets stay a SET. Containers are pin types like UE's (`types.ts`): arrays `T[]` (untyped `array`), maps `Map<K, V>` (`map`; Python `dict[K, V]`, TS `Map` / `Record`, Rust `HashMap` / `BTreeMap`, GDScript `Dictionary[K, V]`) and sets `Set<T>` (`set`; Python `set[T]`, TS `Set`, Rust `HashSet` / `BTreeSet`), read with `arrayElementType`, `mapKeyType` / `mapValueType`, `setElementType` and `iteratedType` (what a loop gets: elements, or a map's keys or pairs). Their pins are drawn with UE's shapes (`container-shapes.ts` in the canvas, `PinIcon.vue` in the panels): a 3×3 grid, a column in the key color beside rows in the value color, braces; maps take the key's color, arrays and sets their element's. Struct-like dictionaries (Python `TypedDict`, dict literals in TS) stay objects. Known operations on a typed container are UE's container nodes too (`container-ops.ts` in core, a `ContainerOp` table per backend in its `container-ops.ts`): a method (`items.push(x)`), property (`items.length`), function (`len(items)`) or operator (`x in items`, `a | b` of sets, Rust's `&a | &b`; `a.union(&b)` is an iterator and stays a call) becomes a compact node with one word (LENGTH, CONTAINS, FIND, INDEX OF, KEYS, VALUES, ADD, INSERT, REMOVE, CLEAR, UNION …; an array's `indexOf` / `index` / `find` is INDEX OF, not UE's FIND, as it returns an index while a map's FIND returns the value). An op's `fixed` values are written as that literal: the call is the op only when written so, and the node hides their pins (TypeScript's `splice(i, 0, x)` is INSERT, `splice(i, 1)` REMOVE INDEX; other splices stay calls; `argsFit`); the call view shows them again (`CallLook.hidden`, named by the signature with the others, `namedContainerNode`), and the menu writes them. An op's `label` shows the language's own word instead of UE's (TypeScript's INCLUDES for arrays, HAS for `Set` and `Map`, both CONTAINS); `containerLabel` reads it, `containerWord` stays UE's for the logic, and the graph search finds either over the container's symbol, the container pin first, values and result typed by the container (`containerPartType`). The backend decides it while lowering the call, when its target's type is known (`findContainerOp`, `findContainerOperator`), so reads are pure like UE's and leave the exec chain, while those that change the container (`mutates`) stay on it; UE's LAST INDEX is an array's LENGTH minus the literal 1 (`len(items) - 1`, `items.length - 1` …): `lastIndexValue` turns that LENGTH node into one LAST INDEX node over the whole subtraction, and the action menu writes it the same way. UE's map FIND also tells whether the key is there: FIND nodes of maps get a `found` output (`addFoundPins`, run by each backend on its finished graph) whose code is the language's CONTAINS of the same map and key (`containsKeyCode`: `"a" in d`, `m.has(k)`, `m.contains_key(&k)`, `d.has(k)`), so wiring it writes that. `x not in items` (Python, GDScript) is CONTAINS wired into NOT, the same nodes as `not x in items` (`GraphBuilder.notInValue`): both cover the whole expression, so CONTAINS keeps `x in items` as its own code (`NodeCodeMeta`, read with `nodeCode`; copied by copy and paste and by wires from it) and NOT's input writes its value as `not $value` (`InputPinMeta.wrap`, applied by `inputEdit`). Deleting, rewiring, promoting and extracting either node keep the code right; promote writes through the input the value fills (`valueEdit`). `styleContainerNode` keeps the word in `meta.container` (`containerWord`, read by `compactTitle`), so titles and ops stay those of the code. Signatures only name their pins (`namedPins`): they take the values they show. The tables also go to the web app (`TypeSystemInfo.containerOps`): the action menu offers each word from a container's output, written the language's way with empty values (`containerEntries` in `graph-canvas/container-entries.ts`; `byReference` writes Rust's `&`, `typeText` keeps TypeScript's `Map` methods off a `Record`), and the graph search finds the nodes by their word. In TypeScript, module variables are typed in functions by their annotation or container value (`DocumentContext.variableTypes`); values typed only later (by the checker, or a backend's own type lookup: Python's `sorted(…)` returns a list) become container nodes in `applyTypes`: the backend marks a call, property read or operator it couldn't type (`markContainerCandidate`), and `restyleContainerNodes` styles it once a wire brings a container type (`CallTyping.containerOps`), taking reads off the exec chain (the exec wire runs from the node before to the node after). The web app lays the graph out again when the checker's types arrive (`relayout`; pinned positions stay). A node picked from the action menu shows as its container node while it floats too: the pin fed by the dragged value takes that value's type when it has none (`withFedType`). Container nodes are only a way to draw calls the code has: a node can be drawn as its call (`push`) instead, remembered in the layout like box colors (`~call|<nodeId>`, `call-views.ts` in core; `styleContainerNode` keeps the call's pin order in `meta.container.call`, `withCallViews` draws it, `reconcileCallViews` follows the node). The node menu switches it ("Show as push() call" / "Show as ADD"), and the action menu's call entries ("items.push(value)", `.push()`) draw their new node as the call, while its container entries (`useValue.container`) draw the container node; the entry moves with a floating node when it is written. Floating nodes keep the wires from the function's parameters their code reads (`items.push(…)` keeps `items` as its receiver); a node picked from a parameter is written with its name instead of the placeholder (`items.push('')`), so the checker types and names its pins like code. The menu writes a method that is a container operation with its values empty (`methodCallExpression`: `.push()` is `$value.push('')`), so the call has its value pins and can be shown as ADD. Entry nodes use the `entry` category (purple) for functions and `event` (red) for code that runs on its own: the module, class bodies, Godot callbacks and `_on_…` signal handlers.
- **Call pins** (`call-pins.ts`): after parsing, calls of the file's own functions get a pin per parameter (`completeCallPins`). Missing arguments are pins without code that insert the argument at the call's `)` (`insertInitAt`), with placeholders for skipped parameters, or `name=` in Python. An argument passed by name (Python's `timeout=5`) is named after its parameter (`timeout`) and marked with `InputPinMeta.keyword`; the pins of a call follow the signature's order (`url`, `data`, `timeout`), whatever order the code passes them in.
- **Result types:** `setReturnType` also adds a Return node at the end of the flow (`endOfFunction` in `flow.ts`) when the function has none, like UE adds one with the first output.
- **Inferred types** (`infer-types.ts`, after the call pins): a Return's untyped value takes the function's declared result, and an untyped variable the type of the value it is declared with (`const t = greet(user)`).
- **Row wrapping:** exec chains wider than `maxRowWidth` continue on a new row, but a node that ends the flow (Return, throw, break, continue) stays on its row. Rows break between statements: a statement of several nodes (a chain `a.b().c()`) starts a new row when it doesn't fit, and never breaks in the middle (unless twice too wide).
- **New nodes and functions:** a node without a saved position follows the node its value feeds (`new X()` with its SET), else the node before it. A function without saved positions in a file that has some (a callback just written) goes right below the placed functions.
- **The grid:** nodes sit with their top-left corner on the 16-unit grid the canvas draws (`GRID_SIZE`, `snapToGrid` in core's `grid.ts`), like in UE: `layoutDocument` snaps the positions it lays out (saved ones stay as they are, so aligned pins and older layouts keep their place), new and floating nodes snap where they are placed, and a drag snaps the grabbed node while the rest of the selection keeps its offset to it.
- **Placing new nodes:** the node an edit asked for goes where the menu was opened; the other new nodes of the same edit (a hoisted call, the parts of an expression) keep their auto-layout offset to it.
- **Function frames** enclose the nodes wired to their entry (`wiredNodes`); a node not wired in yet (a Get just placed) sits anywhere without moving the frame. Nodes the user placed or moved never move other functions, so frames may overlap. Only growth by the code (wired nodes without a saved place, e.g. statements just typed) moves a function down until it is `frameGap` clear of the earlier ones in the same columns (`separateFunction`). Placing or moving the first node saves the whole shown layout, also the nodes the canvas doesn't draw (Gets shown as wires from their SET, implicit `self`), so nothing is laid out anew around it.
- **Signatures** (`signature-ops.ts`): adding, removing, moving, renaming and typing parameters and the return type. Backends report the same-file calls of a function (`callSites`), so arguments stay in sync like UE's call nodes: a new input leaves calls as they are (the missing argument shows as an empty pin; `addParameter.argument` writes a given value), a removed one loses it, a moved one moves it.
- **Symbol ops** (`addFunction`, `addVariable`, `addSignal`, `renameSymbol`, `deleteSymbol`) are placed and validated in core (`symbol-ops.ts`, `symbol-edits.ts`) with each language's `DeclarationSyntax`. A new function goes after the declaration in `after` (My Script passes the function, method or class the user works in: the selected symbol, else the function shown in the graph; `newFunctionAnchor`), otherwise after the file's last function or class when code that runs the module follows it (`main()`, `if __name__ == "__main__":`), else at the end. In languages that run the module from top to bottom (`StatementSyntax.definitionsRunInOrder`: Python, and TypeScript for its classes and `const` functions), a statement added to the module's flow goes below the functions and classes before the next statement, so it can call them (`belowDefinitions` in `insert-ops.ts`). Where a missing argument fails (`StatementSyntax.requiredArguments`: Python, GDScript, Rust), a new call of a known function gets a value for each required parameter: the default of its type when that is a plain value, else the placeholder (`withRequiredArguments`). A node on the False pin of an `if` without `else` writes an `else` holding it at the end of the `if` (`StatementSyntax.elseBranch`; a Branch becomes `elif` / `else if`), unless the pin already leads into an `elif`. Renames are backend specific (`rename.ts`): each resolves the uses of a name with its language's scope rules (block scopes and hoisting in TypeScript, assignment makes a name local in Python, function-wide `var` in GDScript), and renames class members through `this.x` / `self.x`.
- **Comments** are attached in core (`attachComments`). Backends only report the ranges of all comments their parser saw. A comment directly above a statement becomes the node's comment; regions become comment boxes. A deleted statement takes its comment above, a comment after it on the same line (`trailingCommentEnd`, also kept when it moves), and the closing line of a directive its comment opened (`// oxlint-disable` … `// oxlint-enable`, `# fmt: off` … `# fmt: on`: `closingDirectiveEnd`); other comments below it stay, since they may be about the next code. Comments are never stored in the layout.
- **Problems** come from the editor's markers: Monaco's TypeScript worker for TS/JS, plus parser diagnostics set as markers for the other languages. `problemsByNode` maps them to nodes.
- **TypeScript's checker** (Monaco's worker) sees more than the open file (`script-workspace/use-type-libs.ts`, `monaco/project-libs.ts`). It gets the repository files the open file imports, and their imports, three levels deep and at most 60 files. It also gets the declarations of the npm packages these files import: `graph/npm-declarations.ts` reads each package's `package.json` and the `.d.ts` files its types reach from jsDelivr (`@types/<name>` when it has none), and puts them at `node_modules/<name>/…`, where Bundler resolution finds them. The version is the exact one of the nearest lockfile (`pnpm-lock.yaml`, `package-lock.json`, `yarn.lock`), else the range of the nearest `package.json` that lists the package (`graph/npm-project.ts`, which reads the dependencies with their kinds into core's `ProjectDependency`). Only files jsDelivr's listing of the version names are read (`packageFiles`), so nothing is guessed; `/// <reference types="x" />` reads `@types/x` first, imports the package first, unless the importing package depends on one of them. Files that answered 404 are remembered in the browser (`graph/missing-urls.ts`: 30 days for exact versions, a day for `latest` and ranges). The checker's environment follows the file's `tsconfig.json` (`graph/ts-environment.ts`: the nearest one, its relative `extends`, or for a solution-style config the referenced one whose `include` takes the file): `lib` without `DOM` drops the DOM (only `lib.esnext.d.ts`), and Node.js code (`types` with `node`, or no `types` and `@types/node` installed; without a config, imports of Node.js modules) gets the whole `@types/node` in the project's version; `experimentalDecorators` is passed on (NestJS's parameter decorators are errors without it). Monaco has one set of compiler options, so `setTsEnvironment` (`monaco/setup.ts`) switches them with the file on screen; the short Node.js stub there is only used when `@types/node` can't be loaded. The files are Monaco extra libs, shared by the open workspaces and dropped when none uses them anymore.
- **File references** come from the optional `LanguageBackend.references()`. Backends report candidate paths and `resolveModuleReference` picks the first one that exists in the repository. Supported:
  - TypeScript/JavaScript: relative imports, exports, `require()`, `import()` and `new URL(…, import.meta.url)` (`./x.js` finds `./x.ts`, folders find `index.ts`).
  - GDScript: `"res://…"` paths and relative `preload()` / `load()` paths.
  - Python: modules next to the file, in the repository root or relative (`from .utils import x`).
  - Rust: `mod x;` (`x.rs`, `x/mod.rs`) and `use crate::…` / `self::` / `super::` paths; `crate::` starts in the `src` folder next to the nearest `Cargo.toml`.
- **Language version** (status bar, like VS Code) comes from the optional `LanguageBackend.versionFiles` and `version()`. The web app reads those files in the folder of the open file and every folder above it (`projectFilesAbove`), and the backend picks the version from the nearest one that states it. The playground has no project files, so it shows the language only.
  - TypeScript/JavaScript: `typescript` in `package.json` (also through pnpm catalogs in `pnpm-workspace.yaml`).
  - Python: `.python-version`, then `pyproject.toml` (`[tool.pyright] pythonVersion`, `[tool.mypy] python_version`, `requires-python`, Poetry's `python`), `setup.cfg` `python_requires`, `runtime.txt`.
  - GDScript: the feature tag in `project.godot` (`config/features`), else its `config_version` (5 = Godot 4).
  - Rust: `edition` and `rust-version` of the crate's `Cargo.toml` (inherited from `[workspace.package]`, 2015 when missing), or a version pinned in `rust-toolchain(.toml)`.

### Persistence

| Data                              | Where                                                                                            |
| --------------------------------- | ------------------------------------------------------------------------------------------------ |
| Node positions and reroute points | `file_layouts`, per repository, branch and file, shared by all users                             |
| Workbench layout                  | `user_preferences` (key `workbench.layout`), cached in the browser                               |
| Recently opened projects          | `recent_projects`, the newest 20 per user                                                        |
| Library types (npm, typeshed)     | `type_cache`, shared by all users; least recently used rows go past `TYPE_CACHE_MAX_BYTES`       |
| Unsaved code edits                | Local draft in the browser                                                                       |
| Local folders                     | Handles in IndexedDB (`vizscript` → `folders`), their layouts and drafts in browser storage      |
| Open tabs                         | Browser storage per repository branch or local folder; their Monaco models stay alive while open |
| Camera, color scheme              | URL (`?view=x,y,zoom`) and browser storage                                                       |

Repositories are keyed by the provider's numeric id, so layouts survive renames. The playground uses browser storage only.

Open files, tabs and drafts of a repository branch or local folder are one shared session (`composables/use-file-session.ts`, used by `RepoView` and `LocalProjectView`), keyed by its scope (`github/<owner>/<repo>@<ref>`, `local/<id>`): `vizscript:tabs:<scope>` and `vizscript:draft:<scope>:<path>`. A draft holds `{ version, text, overlay }`, where `version` is the blob sha (repositories) or a short hash of the file's text (`textVersion`, local folders); it is restored only for the same version. A draft of an older version is kept aside under `…#outdated` and offered next to the file name (Restore puts its text on top of the current version, Discard drops it), never dropped silently. `changedFiles` lists every file of the scope with unsaved changes (open buffers and stored drafts) for the explorer's marks; the code editor marks lines changed against the saved text (`baseText`, `graph/line-changes.ts`, `monaco/line-change-gutter.ts`). Files are created, renamed and deleted from the explorer (`FileTree`'s name field and context menu). Local folders do it on disk (`LocalProject.create` / `rename` / `remove`; a rename copies, then removes, as `move()` isn't there for every folder); repositories keep it as `TreeChanges` (`graph/tree-changes.ts`, stored as `vizscript:tree:<scope>` by `composables/use-tree-changes.ts`): new paths with the file they were moved from (`''` for a new file, which reads empty), deleted repository files (listed struck through until restored) and empty new folders. Either way the session's `movePath` / `forgetPath` move or drop the tabs, unsaved text and drafts of the files.

Per-file browser data (drafts, local layouts, cameras, tabs) goes through `storage/browser-storage.ts`: `writeStored` wraps it in `{ v, at, data }` (`STORAGE_VERSION`), `readStored` checks it with a parser and also reads entries from before the envelope, and leaves entries of a newer version alone. `pruneStored` removes entries not written for a while (drafts and file changes 90 days, layouts 180, cameras 60, tabs 120) once per page load; when the storage is full it first frees old entries (not drafts or file changes), then tells the user once. Local folder handles share one IndexedDB connection that closes when another tab upgrades the database.

### Signed in or not

Signing in is optional. Without a session:

- **Reading repositories:** the web app reads public repositories straight from GitHub without a token (`apps/web/src/api/github-public.ts`, chosen by `repoSource`), so every visitor has GitHub's 60 requests per hour of their own IP instead of sharing the server's. Files come from the raw host (`ClientConfig.github.rawUrl`, no API request; their git blob sha is computed in the browser), so only the repository, its tree and its branches count. The status bar shows the requests left (`GithubLimitStatus`, in `#workbench-status-end`): it updates from the headers of each request and polls GitHub's free `/rate_limit` every minute while the page is visible, which also counts requests of other tabs and notices the hourly reset. `GET /api/config` tells the web app where GitHub is (`GITHUB_API_URL`, `GITHUB_RAW_URL`, `GITHUB_WEB_URL`, e.g. GitHub Enterprise in an internal network). The web app never guesses public GitHub: until the config is loaded (`githubConfig`, tried again after a failure) it sends no GitHub request, shows no repository images (`resolveImage` takes the raw host) and links to no token page.
- **Type registry:** `GET /api/types?path=…` and `/api/types/listing?path=…` serve library type files and listings by jsDelivr's paths (`npm/<name>@<version>/<file>.d.ts`, typeshed at a commit), from `type_cache` (`types/type-cache.service.ts`). Only declaration files of npm packages and typeshed's pinned commit are allowed (`types/type-sources.ts` builds the upstream URL from the validated parts). Exact versions are kept until evicted, version ranges (`latest`, `^3.5.0`) for a day, 404s too. Eviction drops the least recently used rows once the total passes `TYPE_CACHE_MAX_BYTES`; the table may be truncated any time. Each client IP may make the server fetch 5000 files per 10 minutes (429 after). `GET /api/types/crate?name=…&version=…` serves a Rust crate's public API: docs.rs's rustdoc JSON (zstd, read on the server as browsers can't) turned into Rust declarations per module (`types/rustdoc.ts`: functions, structs, enums, traits, aliases, constants, inherent `impl` blocks, `pub use` re-exports followed), cached like the files; a version without rustdoc JSON (built before docs.rs made it) falls back to the newest compatible one for a day. The web app parses a module's declarations with the Rust backend for `use` imports (`graph/crate-types.ts`, `rustExports` in `use-imports.ts`), in the version of `Cargo.lock`. `GET /api/types/pypi?name=…&version=…` serves a Python package's own types (PEP 561): the `.pyi` files and the `.py` files of `py.typed` packages of a wheel of its release on PyPI (`types/wheel.ts` reads the zip with zlib; a pure-Python wheel first, only from PyPI's file host); an exact version from the lockfile or a `==` pin, else the latest, for a day. The web app resolves them like typeshed's stubs (`packageSource` in `graph/python-stubs.ts`, `graph/pypi-types.ts`) and puts them before typeshed's stubs of the same package. `GET /api/types/search?ecosystem=npm|crates|pypi&q=…` searches libraries to add (npm's and crates.io's search, PyPI by exact name), cached in memory for 10 minutes. `GET /api/types/stats` reports entries, bytes, the limit and the hit rate since the start. The web app uses it when `/api/config` says `typeRegistry` (`graph/type-registry.ts`) and reads jsDelivr directly when it isn't there or fails.
- **Layouts:** `GET /api/layouts/…` works without a session for public repositories (`OptionalSessionGuard`) and writes nothing: a repository gets its row in `repositories` with the first saved layout. A signed-out visitor of a repository without stored layouts gets an empty layout without a provider request (the same answer as for a missing or private one); otherwise `RepoAccessService` checks that it is public, with the server's token if `GITHUB_SERVER_TOKEN` is set (else none, the server's own 60 requests per hour), cached for an hour. Changing a shared layout needs a session and push access (`RepoAccessService` asks the provider with the user's token, cached for 5 minutes; `LayoutResponse.canWrite`); "no access" and "not found" are cached for 5 minutes too, a rejected token is not. Without it, `repoLayoutStore` keeps the user's moves in browser storage on top of the shared layout.
- **Recent projects** stay in browser storage (`vizscript:recent`), the **workbench layout** in its browser cache; drafts are local either way.

Signed in, the API reads through the user's stored token (private repositories, 5,000 requests per hour) and keeps recent projects and preferences per user.

**When sign-in stops working:** every 401 carries a reason (`ApiError.code`, `AuthErrorCode` in `@vizscript/api-contract`, made by `authError` in the API): `not_signed_in`, `session_expired` (a session cookie whose session is gone; also on `OptionalSessionGuard` routes, and the cookie is cleared), `provider_token_missing` and `provider_token_invalid` (GitHub rejected the stored token, e.g. an expired fine-grained token). The web client hands them to one handler (`setAuthErrorHandler`, registered by the session store): a signed-in user is signed out with one message saying why, and the repository view reloads through the public source. Shared layouts tell an unreachable server (no answer, 5xx) from lost access: while unreachable, moves are kept as pending (`vizscript:layout:pending/…`) and sent with the next load that works; without write access they stay in this browser.

### Extension points

- **Languages:** implement `LanguageBackend` (`parse` + `applyOp`, optionally `references`) and register it in `apps/web/src/graph/registry.ts`, plus the extension in `languages.ts` and a Monaco grammar if Monaco lacks one.
  - `parse` lowers the AST to the graph IR and attaches edit metadata (`StatementMeta`, `InsertPoint`, … in `@vizscript/core`). Shared graph building lives in `GraphBuilderBase`; backends add the AST walk.
  - `parse` also fills `symbols` (see `summarizeSymbols` for snapshot tests) and calls `linkSymbolGraphs`.
  - `applyOp` is usually just `applyTextOp(text, doc, op, SYNTAX)`. A `StatementSyntax` describes placeholders, declarations, quoting, comments and templates.
  - Parsers must run in the browser worker. Python and Rust use `@lezer/python` / `@lezer/rust` (pure JS, error tolerant); GDScript has a small hand-written parser.
  - Rust specifics (`lang-rust`): a block's last expression is the function's value and becomes a Return node; macro arguments (`println!`, `format!`, `vec!` …) are parsed as expressions on their own; `if let` / `while let` and match arms get output pins for the names their pattern binds; methods go into the type's inherent `impl` block (a new one when there is none), fields into the struct; parameters have no defaults (`TypeSystemInfo.noParameterDefaults`); the placeholder is `todo!()`.
- **Source providers:** implement `ScmProvider` in `apps/api/src/scm/` and add it to the `SCM_PROVIDERS` factory.
- **Identity:** login goes through `AuthService.loginWithToken`. An OIDC login can reuse the same user, identity and credential tables.
- **Local folders** (`apps/web/src/local/`) are read in the browser with the File System Access API, so nothing goes through the API. `LocalProject` hides whether a folder has a handle (Chrome, Edge: remembered, writable) or comes from `<input webkitdirectory>` (other browsers: read-only, this tab only). Listing skips `.git`, `node_modules` and the root `.gitignore` rules.
- **Layout storage:** the web app talks to a `LayoutStore` interface, with an API-backed and a `localStorage` implementation.

## Verifying a change

CI runs install (frozen lockfile), lint, format check, type check, build, the tests against Postgres on Node 24 and 26, and a Docker image build. Locally:

```sh
pnpm db:up && pnpm preflight
set -a && . ./.env && set +a && pnpm exec vitest run   # includes API e2e tests
```

- **Web logic:** `apps/web/test` tests the web app's plain modules and its workspace composables without the UI (placement, via wires and pure joins, graph-only and loose nodes, undo history). `fake-client.ts` answers the worker's requests in place with the TypeScript backend, `settle()` lets their promises finish.
- **Snapshots:** graph lowering uses readable snapshots (`summarizeGraph`). `pnpm preflight` updates them; review the diff.
- **Parser changes:** run the corpus checks against a real project, e.g. `GD_CORPUS=/path/to/godot/project pnpm exec vitest run packages/lang-gdscript` (and `PY_CORPUS=… packages/lang-python`, `RS_CORPUS=… packages/lang-rust`). They fail on any diagnostic.
- **Naming UI parts:** important containers have a `data-ui` name (`workspace-toolbar`, `view-graph`, `details-panel`, …); search the inspector for `data-ui` to find them. New panels, toolbars, menus and dialogs get one too.
- **UI changes:** check them in the running app, especially the playground, in light and dark mode. The repository's `.mcp.json` sets up the Playwright MCP for AI agents. The Claude Code skill `/viz-user-test <playground URL or sample>` (`.claude/skills/viz-user-test`) acts like a user: it rebuilds a sample by hand in the graph, then edits it at random, and writes its findings to `local/`.
- **Local folders without the folder picker:** in an automated browser, create a folder in the origin private file system (`navigator.storage.getDirectory()`), put `{ id, name, openedAt, handle }` into the `folders` store of the `vizscript` IndexedDB and open `/local/<id>/<file>`. Write to the folder from the page to imitate changes made outside the app, and remove the record, the folder and the `…local/<id>…` storage keys afterwards.

## Commits and pull requests

- Use [conventional commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `chore:` …); PR titles are validated.
- Keep titles at most 64 characters, so they stay under 72 with a `(#1234)` suffix.
- Prefer small commits with a clear scope, and keep every commit green in CI on its own.
- Database changes need a migration (`pnpm migrate create <name> -j ts`).
- Bugs and feature requests go through the [issue forms](https://github.com/Shinigami92/vizscript/issues/new/choose).
